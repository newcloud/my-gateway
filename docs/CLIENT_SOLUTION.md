## 0. 30 秒读懂

**问题**：系统的接口到底有哪些、谁能访问、能传什么字段，往往没人说得清。WAF 拦得住通用攻击，拦不住"多传一个 `is_admin`"。

**方案**：把后端已有的接口清单（我们称为"接口契约"）变成网关上的**白名单**。没登记的路由、没声明的方法、没列举的字段，一律拒绝。规则写在 nginx 侧，后端改不了。

**三个特点**：

1. **不换网关、不改后端**——在现有 nginx 上加一个模块，后端代码一行不用动；
2. **默认拒绝**——扫描器连"这个接口存不存在"都探不到；
3. **可先观察后强制**——先看两周报告，觉得没问题再开拦截，不影响业务。

**投入**：单系统 POC 4 周，试点 1–2 个月，可分批推广到全单位。

## 1. 现状：四个绕不开的问题

| # | 问题 | 典型表现 | 现在的做法为什么不够 |
| --- | --- | --- | --- |
| 1 | **接口家底不清** | 测试接口、调试接口、老版本接口留在线上；每年 HW 都要重新摸一遍 | 文档靠人写，写完就过期；扫描器只能猜路径 |
| 2 | **字段级越权** | 前端多传 `is_admin: true`、`balance: 0`、`status: 99`，后端直接落库 | WAF 看不懂 JSON 结构；后端各团队写法不一，改造周期长 |
| 3 | **变更无台账** | 谁在什么时候放开了哪个接口，出了事说不清 | 各系统配置分散，缺少统一、可追溯的边界策略 |
| 4 | **后端被攻破即失守** | 攻击者拿到应用权限后，可顺手改掉网关规则或直连后端 | 规则如果来自被保护的系统本身，等于没有边界 |

这四条，**没有一条能靠"加强开发规范"落实**，因为它们都需要一个**运行时的强制点**。

## 2. 根因：三张皮

| 皮 | 是什么 | 后果 |
| --- | --- | --- |
| 文档 | Swagger / Word / 接口清单 | 与实现不一致，且从不参与决策 |
| 实现 | 后端代码里的真实路由与字段 | 只有开发和攻击者知道全貌 |
| 防护 | WAF / 防火墙 | 按特征猜，不知道业务接口应该长什么样 |

**三张皮无法通过流程缝合，只能通过一个"以接口清单为准"的执行点合并。**

## 3. 方案：把接口清单变成白名单

### 3.1 原理

```
                 ┌───────────────────────────────┐
   客户端 ──────► │  nginx + 边界管控模块          │ ──────► 后端业务系统
                 │                               │
                 │  1. 这条路由登记过吗？          │
                 │  2. 这个方法允许吗？            │
                 │  3. 这些字段声明过吗？          │
                 │  4. 大小/类型/格式合规吗？      │
                 └───────────┬───────────────────┘
                             │ 读取接口清单（本地文件/后端接口）
                             ▼
                    ┌──────────────────┐
                    │  接口契约（白名单）│
                    └──────────────────┘
```

一条请求进来，网关按顺序判定：

| 判定 | 不通过时 | 说明 |
| --- | --- | --- |
| 路由是否登记 | `404` | 未登记路由直接拒绝，请求不进入后端 |
| 方法是否允许 | `405` + `Allow` | 例如只允许 `GET`，`POST` 一律拒绝 |
| 字段是否声明 | `400` | 写接口多传字段直接拒绝（防越权赋值） |
| 大小/类型/格式 | `400` / `413` | 请求体上限、必填、长度、范围、枚举、格式 |

所有拒绝都会产生一条可关联的审计日志（含唯一 `X-Request-Id`），便于事后追溯。

### 3.2 三种运行模式：先看、再试、后拦

| 模式 | 做什么 | 请求结果 | 适用阶段 |
| --- | --- | --- | --- |
| **观察** | 只统计、不判定 | 全部放行 | 接入第一周：摸清接口家底、出报告 |
| **影子** | 判定但不拦，记录"本应拦截" | 全部放行 | 上线前 1–2 周：验证规则有没有误判 |
| **强制** | 判定并拦截 | 违规拒绝 | 正式运行 |

**这套模式是方案的落地关键**：它让"引入一套强制策略"从"可能影响业务"变成"先看报告、再灰度"。

### 3.3 为什么不需要改后端

| 需要后端配合的常见方案 | 本方案 |
| --- | --- |
| 在代码里加注解、生成 OpenAPI | 不需要；存量系统也可用 |
| 改造框架、重新发版 | 不需要；网关侧独立部署 |
| 逐个团队推动 | 只需一次接口清单梳理（可自动生成候选） |

对存量系统，这是"能不能落地"的分界线。

## 4. 典型使用场景

### 场景一：政务门户 / 一网通办（对外开放接口）

- **现状**：对外发布的接口多、版本多，历史接口难以下线；每年 HW 是被扫描重点。
- **风险**：未登记接口被直接访问；旧版本接口缺少鉴权。
- **上线后**：未登记路径一律 `404`，扫描器拿不到任何有效信息；旧接口下线只需从清单移除，立即生效。
- **对应能力**：路由白名单、方法白名单、统一拒绝日志。

### 场景二：内网业务系统（OA / 审批 / 财务 / 人事）

- **现状**：内网被认为"安全"，接口清单常年不更新；横向移动一旦发生，攻击者可以逐个试接口。
- **风险**：内网失陷后，攻击面等于全部未登记接口。
- **上线后**：内网也按白名单运行，异常探测在内网同样被拒绝；日志可定位"谁在探接口"。
- **对应能力**：默认拒绝、探测行为留痕。

### 场景三：数据共享交换平台 / 数据中台

- **现状**：对外提供数据查询与推送，字段多、来源杂。
- **风险**：调用方多传字段、越权取数；"最小必要"难以证明。
- **上线后**：每个接口声明允许的字段集合，未声明字段直接拒绝；可输出"字段级访问台账"，用于数据安全检查。
- **对应能力**：字段白名单（`unknown: reject`）、必填与格式校验、访问日志。
- **对应合规**：数据安全法、个人信息保护法的"最小必要"原则。

### 场景四：第三方对接 / 开放平台

- **现状**：外部厂商接入，接口约定靠文档；对方升级版本后行为漂移。
- **风险**：对方多传字段导致后端异常；接口被非授权方调用。
- **上线后**：接口契约成为双方共同遵守的边界，越界请求在网关被拒并留证。
- **对应能力**：字段/方法/大小限制、按来源 IP 或凭证区分策略（需与现有鉴权体系配合）。

### 场景五：HW / 护网期间

- **现状**：临时收紧策略，靠人盯日志、靠 WAF 规则临时加。
- **风险**：临时规则容易误伤；活动结束后无人回滚。
- **上线后**：白名单常年在位，HW 期间只需确认"清单是否最新"；拒绝日志可直接作为防守成果。
- **对应能力**：默认拒绝、稳定拒绝原因、日志统计。

### 场景六：等保测评整改

- **现状**：测评提出"边界访问控制不细、审计不完整"，整改往往落到"再买一台设备"。
- **上线后**：在不改变现有网络架构的前提下补齐边界访问控制与审计证据。
- **对应能力**：访问控制（路由/方法/字段）、安全审计（结构化日志 + 唯一请求 ID）、入侵防范（未声明即拒绝）。
- **说明**：本方案是**技术措施之一**，不替代等保要求的其他控制项。

### 场景七：老旧系统 / 无法改造的系统

- **现状**：语言老旧、厂商已停止维护、没人敢改代码。
- **风险**：明知接口多余也不敢动。
- **上线后**：在网关侧收敛暴露面，**不动一行业务代码**。
- **对应能力**：全部能力均可在网关侧完成。

### 场景八：微服务 / 容器化后的东西向流量

- **现状**：服务数量增长快，服务间调用缺少统一边界。
- **风险**：任一服务被攻破后可横向调用其它服务接口。
- **上线后**：在每个服务的入口（或 Ingress 层）挂同一套白名单策略，形成"最小接口暴露"。
- **说明**：适用于已使用 nginx / Ingress 的架构；纯 Service Mesh 环境需评估接入点。

## 6. 与现有安全设备的分工

客户最关心的问题：**"是不是又要买一套？和 WAF 什么关系？"**

| 设备 | 管什么 | 与本方案的关系 |
| --- | --- | --- |
| 防火墙 | 网络层放行/阻断 | 互补：防火墙管"能不能到"，本方案管"到了能做什么" |
| WAF | 通用攻击特征（黑名单） | **互补且不重叠**：WAF 不知道你的接口该收哪些字段；本方案是业务白名单 |
| API 网关 | 鉴权、限流、路由转发 | 可共存：本方案可作为其前置/后置的边界校验层，不抢它的职责 |
| IDS / 态势感知 | 发现异常流量 | 本方案的拒绝日志可作为其数据源 |
| 堡垒机 / 4A | 运维侧身份与审计 | 互不替代：一个管人，一个管接口 |
| 代码审计 / 渗透测试 | 发现漏洞 | 本方案限制漏洞被利用的**路径**，不修复漏洞本身 |

**一句话**：WAF 是黑名单，本方案是白名单；前者拦"已知的坏"，后者只放"声明的对"。

## 7. 部署与实施

### 7.1 部署形态

| 形态 | 说明 | 适用 |
| --- | --- | --- |
| 单机模块 | 在现有 nginx 加载模块，读取本地接口清单 | 单系统、试点 |
| 双机/集群 | 各节点加载同一份清单，按现有 nginx 集群方式部署 | 生产 |
| 旁路观察 | 通过镜像流量或访问日志分析，不改变现网路径 | POC 第一阶段 |

**资源占用**：模块随 nginx 进程运行，无独立进程、无额外网络跳转；具体指标以 POC 实测为准。

### 7.2 实施路径（建议四阶段）

| 阶段 | 周期 | 主要工作 | 交付物 | 验收标准 |
| --- | --- | --- | --- | --- |
| 一、观察 | 1–2 周 | 接入流量/日志，梳理真实接口 | 《API 资产与暴露面报告》 | 报告经客户确认，列出未登记接口 |
| 二、影子 | 1–2 周 | 部署模块，开启判定不拦截 | 《误判清单与规则修订记录》 | 误判率 < 0.1%，客户确认清单 |
| 三、试点 | 2–4 周 | 选 1–2 个非核心系统强制拦截 | 《试点运行报告》 | 连续 2 周无业务中断 |
| 四、推广 | 按系统分批 | 逐步覆盖核心系统 | 《运行手册》《应急预案》 | 按批次验收 |

### 7.3 风险控制与回滚

| 风险 | 控制措施 |
| --- | --- |
| 规则漏声明导致合法请求被拒 | 影子期先验证；强制期按系统灰度；保留一键回滚 |
| 接口清单过期 | 变更流程纳入发布环节；提供清单与真实路由的差异检查 |
| 性能影响 | 先做压测基线；body 校验按接口开启，不全局强制 |
| 单点故障 | 沿用现有 nginx 高可用架构；模块无独立状态 |
| 误拦核心业务 | 白名单支持按路径临时放行（需审批并留痕） |

**回滚方式**：移除该 location 的策略绑定并 reload，立即恢复原行为；不涉及数据变更。

## 10. POC 方案与验收标准（建议写入合同）

| 项 | 内容 |
| --- | --- |
| 范围 | 选定 1 个系统、1 个业务域（建议含 1 个写接口） |
| 周期 | 4 周（观察 1 周 + 影子 1 周 + 强制 2 周） |
| 环境 | 测试或准生产环境；由客户提供流量镜像或访问日志 |
| 客户配合 | 接口清单确认人 1 名、网络与运维支持 |
| 我方交付 | 部署、清单初稿、报告、运行手册、培训 1 次 |

**建议验收条款**：

1. 未登记路由访问返回 `404`，且后端访问日志中**无该请求**；
2. 写接口多传未声明字段返回 `400`，后端无该请求；
3. 合法业务请求在强制模式下通过率 **100%**（以影子期基线为准）；
4. 每次拒绝均可通过请求 ID 在审计日志中定位；
5. 开启校验后接口 P99 延迟增幅不超过 __%（POC 实测后填写）；
6. 回滚操作可在 __ 分钟内完成并验证。

## 11. 常见问题（FAQ）

**Q1：需要后端改代码吗？**
不需要。网关侧独立完成；接口清单可由我方协助梳理，或从现有文档/流量生成候选。

**Q2：会不会误拦正常业务？**
先观察、再影子、后强制，三阶段灰度；影子期专门输出"本应拦截"清单供业务确认；强制期支持按路径临时放行。

**Q3：上新接口怎么办？**
在清单里增加一条并发布，通常 5 分钟内生效；建议纳入现有发布流程。

**Q4：和 WAF 有什么区别？**
WAF 按攻击特征判断，是黑名单；本方案按业务声明的接口与字段判断，是白名单。两者互补。

**Q5：接口清单谁维护？**
建议由系统负责人维护、安全部门审核；我方提供模板、校验工具和培训。

**Q6：后端被攻破后，攻击者能改规则吗？**
推荐使用本地文件作为清单来源：规则由运维发布、后端进程只读，后端被攻破也改不了边界。

**Q7：性能影响多大？**
模块在 nginx 进程内运行，无额外网络跳转；body 校验按接口开启。具体数据以 POC 压测为准。

**Q8：支持信创环境吗？**
可基于国产操作系统与国产 CPU 重新构建，需在 POC 阶段确认目标环境组合。

**Q9：支持国密吗？**
国密 TLS 建议由前置国密网关/密码机完成卸载，本方案与其对接。

**Q10：出问题怎么回滚？**
解除策略绑定并 reload，立即恢复原行为；无数据变更、无版本升级。

## 13. 商务模式

- **POC**：按 §10 范围实施，验收标准写入合同；
- **试点**：按系统或按业务域授权；
- **推广**：按"被保护接口数量"或"节点数量"授权，支持分批扩展；
- **服务**：接口梳理、清单维护、等保测评配合、应急响应，可按年订阅；
- **私有化**：全部组件本地部署，支持离线授权，不依赖外网。

## 附录 A：能力边界（如实声明）

为避免实施阶段出现预期偏差，以下事项**明确不在本方案范围内**：

1. **不做业务规则校验**：库存、状态机、金额、权限判断仍由后端负责；
2. **不替代鉴权系统**：只校验凭证"是否携带、格式是否正确"，不校验"是否有权"；
3. **不替代 WAF**：不提供通用漏洞特征库与虚拟补丁；
4. **不能自动理解业务**：接口清单必须存在，观察模式可降低梳理成本但不能完全免人工确认；
5. **不修复漏洞**：只限制漏洞被利用的路径；
6. **国密 TLS、集中管理平台、监控对接**：属选配或商业版能力，需单独确认交付范围。

## 附录 B：术语

| 术语 | 含义 |
| --- | --- |
| 接口契约 / 接口清单 | 声明了路由、方法、字段与规则的 JSON 文件，是白名单的唯一来源 |
| 观察模式 | 只统计不判定，用于摸清家底 |
| 影子模式 | 判定但不拦截，用于验证规则 |
| 强制模式 | 判定并拦截 |
| 未登记接口 | 实际存在但清单中未声明的接口 |
| 字段白名单 | 写接口只接受声明过的字段，多传即拒绝 |
