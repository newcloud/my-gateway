# 产品化方案：契约白名单型 API 边界网关

> 状态：**方向稿**（2026-10-26）。本文只讨论“这东西卖给谁、凭什么卖、还差什么”，
> 不重复协议细节（见 [PROTOCOL.md](PROTOCOL.md)）和实现进度（见 [PROGRESS.md](PROGRESS.md)）。
> 文中“已有 / 部分 / 缺失”以当前仓库代码为准。

---

## 0. 一页摘要

- **一句话**：把后端自己的 API 契约变成 nginx 侧的白名单，未声明的路由、方法、字段一律拒绝；
  默认拒绝，规则与被执行对象分离，不换网关、不改后端。
- **买家**：政企的安全/合规部门（等保、密评、HW、关基），不是后端团队。
- **卖点**：WAF 是黑名单，我们是白名单；而且这份白名单是业务自己声明的。
- **入场方式**：先做**旁路观察 + API 资产测绘报告**（零改造），再切影子模式，最后强制。
- **护城河**：默认拒绝 + 规则与被保护对象分离 + 不换网关，三条叠加。
- **最大缺口**：观察/影子模式、路由发现、管理面、国密、可观测性。

---

## 1. 问题定义

甲方真正在意的不是“代码有没有 bug”，而是下面四件事，按出现频率排序：

| 问题 | 现实表现 | 现有手段为什么不够 |
| --- | --- | --- |
| **接口暴露面不可控** | 测试接口、调试接口、老版本接口留在线上；扫描器一扫一个准 | WAF 不认识业务接口，只能按特征猜；资产测绘工具只“看”不“拦” |
| **字段级越权（Mass Assignment）** | 前端多传一个 `is_admin: true` / `balance: 0`，后端直接落库 | WAF 看不懂 JSON 结构；后端各团队写法不一，改造成本高 |
| **接口变更不可审计** | 谁在什么时候放开了哪个接口，没人说得清 | 网关配置散落在各系统，变更无台账 |
| **被攻破后的横向移动** | 后端被拿下，攻击者顺手改网关规则 | 规则如果来自被保护对象本身，等于没有边界 |

第 2 条和第 4 条是这类产品真正的立足点：**它们不是 WAF 能解决的问题，也不是靠“开发规范”能落实的问题**。

## 2. 定位

### 2.1 是什么

一个 **nginx 动态模块**（以及配套的离线校验 CLI），把契约变成请求路径上的强制白名单：

- 路由不存在 → 404（不是转给后端让它自己 404）；
- 方法不符 → 405 + `Allow`；
- 写接口出现未声明字段 → 400（防 Mass Assignment）；
- 所有拒绝都有稳定的 `reason` 和可关联的 `X-Request-Id`，进审计日志。

### 2.2 不是什么

| 不是 | 原因 |
| --- | --- |
| 不是 WAF | 不做通用攻击特征库；只做“这份 API 该长什么样” |
| 不是 API 网关替代品 | 不抢鉴权、限流、路由转发、协议转换的生意；塞进甲方现有 nginx |
| 不是业务规则引擎 | 库存、状态机、金额、权限一律不做（见 §8） |
| 不是 API 文档平台 | 契约是执行用的白名单，不是给人看的说明书 |
| 不是零配置产品 | 契约必须存在；产品要做的是把“写契约”的成本压到接近零 |

### 2.3 为什么是 nginx 模块，而不是独立网关

| 维度 | nginx 模块（本方案） | 独立网关 |
| --- | --- | --- |
| 甲方改造成本 | 换一个 `.so` + 改配置 | 流量割接、采购、测评，周期以年计 |
| 性能 | 进程内，无额外网络跳数 | 多一跳，容量要重新规划 |
| 语言/运行时 | Rust，无 GC、无 JVM、内存安全 | 多为 JVM/Lua，资源占用高 |
| 弱点 | 受 nginx 生命周期约束（reload、worker 模型） | 独立控制面更灵活 |

政企场景里“不换网关”是决定性的：**甲方的网关往往已经是某厂商的资产，动它要走一次采购。**

## 3. 目标客户与采购触发点

| 触发点 | 甲方要交的东西 | 本产品对应能力 |
| --- | --- | --- |
| **HW / 护网** | 不能有未登记接口、不能被打穿 | 未声明路由 404；扫描器拿不到任何信息 |
| **等保 2.0 三级/四级** | 边界防护、访问控制、安全审计、入侵防范 | 白名单 + 稳定 reason + 可关联审计日志 |
| **密评（商用密码应用安全性评估）** | 国密 TLS、密码模块合规 | ⚠ 当前**缺失**，是硬门槛（见 §9） |
| **数据安全法 / 个保法** | 最小必要、字段级管控 | `unknown: reject` 直接对应“不多收一个字段” |
| **关基保护** | 资产台账、变更可追溯 | 契约 = API 资产清单，带版本与 diff |

买家里最关键的两个人：

- **安全负责人**：关心“HW 期间别出事、测评能过”；
- **系统负责人**：关心“别给我增加工作量、别影响可用性”。

产品必须同时满足这两者，否则内部就会互相否决。这也是为什么“零改造 + 观察模式”是入场券。

## 4. 价值主张

### 4.1 WAF 是黑名单，我们是白名单

WAF 永远不知道你的 `/api/orders` 该收哪些字段，只能按特征猜；契约知道。
对甲方的一句话：**“不是拦得更多，是只放该放的。”**

### 4.2 默认拒绝，而不是“命中才校验”

常见的 schema 校验插件是“路由注册了才校验，没注册的照样转发”。本方案把未声明本身当作拒绝理由：

- 扫描器扫到的路径 → 404，不产生后端负载；
- 新上线的接口如果没进契约 → 立即暴露（这正是治理想要的）。

### 4.3 规则与被保护对象分离

契约来源有两种，安全性不同：

| 来源 | 信任模型 | 适用 |
| --- | --- | --- |
| `gateway_info_url`（后端 `/info`） | 后端说了算；后端被拿下就能改规则 | 内部、开发阶段 |
| `gateway_info_file`（本地文件） | 只有能写文件的人能改规则；后端进程只读 | 政企生产（推荐） |

第二种在等保语境里就是“安全管理中心与计算环境分离”，评审专家听得懂，也是竞品普遍没做的点。

### 4.4 不换网关、不改后端

一个 `.so`、一段配置。对存量系统，这是“能不能进场”的分界线。

## 5. 产品形态：三种运行模式

这是整套产品最关键的形态设计。**观察模式是获客入口，强制模式才是价值实现。**

| 模式 | 判定 | 请求 | 输出 | 用途 |
| --- | --- | --- | --- | --- |
| **观察（observe）** | 不做（或只做路由学习） | 全部放行 | 路由清单、参数画像、候选契约 | 零改造入场、出测绘报告 |
| **影子（shadow）** | 做，但不拦 | 全部放行 | `would_block reason=... field=... rid=...` | 上线前验证契约、灰度 |
| **强制（enforce）** | 做，且拦 | 拒绝 | 现行行为（404/405/400 + 审计日志） | 生产 |

现状：仓库里只有“强制”，以及 `unmatched: "forward"` 这个粗粒度的放行阀门。
**观察和影子都缺失**，这是 P0。

## 6. 与竞品对比

| 对手类型 | 代表 | 他们的强项 | 我们的差异 |
| --- | --- | --- | --- |
| WAF | 雷池、绿盟、安恒、F5、Imperva | 特征库、虚拟补丁、旁路部署 | 我们有业务自己的白名单；他们不懂 JSON 字段语义 |
| API 网关 | APISIX、Kong、云厂商 API 网关 | 鉴权、限流、可观测性、生态 | 它们命中才校验；且要迁流量过去。我们不换网关 |
| API 安全 | 星阑、永安在线、Noname | 流量侧资产测绘、敏感数据识别 | 他们只“看”不“拦”；我们能在同一套规则上从观察到拦截 |
| 研发侧治理 | Swagger/OpenAPI 平台 | 文档、Mock、协作 | 文档不执行；我们执行的是同一份事实 |

结论：**单点能力都不新，组合方式新**——“不换网关 + 默认拒绝 + 观察入场 + 规则与对象分离”。
这四条同时做到的厂商很少，因为前两条和第三条在商业上互相矛盾（观察入场意味着短期不产生安全价值）。

## 8. 设计原则（决定产品边界）

### 8.1 只描述 HTTP 边界，不描述业务

| 层次 | 管不管 | 理由 |
| --- | --- | --- |
| 路由存在性、方法 | ✅ 必须 | 白名单，成本 1 行 |
| Content-Type、大小上限 | ✅ 必须 | 边界属性，与业务无关 |
| 字段集合（`unknown: reject`） | ✅ 写接口强制 | 只有“列举之外一律拒绝”能防 Mass Assignment |
| 必填、粗类型 | ✅ 写接口强制 | 边界错误 |
| 长度/范围/枚举/正则 | 🟡 按需 | 只在安全或 DoS 有意义时写，不重复业务校验 |
| 库存、状态机、金额、权限 | ❌ 禁止 | 写了就是第二套业务逻辑，必然漂移 |

**契约会变成一份“规范”，这是 fail-closed 的必然结果，改不了。** 能做的是把规范的范围压到最小：
只覆盖 HTTP 边界（稳定、字段少），不覆盖业务（天天变）。

### 8.2 让规范的维护成本接近零

| 契约来源 | 谁维护 | 开发者负担 | 漂移发现 |
| --- | --- | --- | --- |
| 手写 | 安全/运维 | 加接口要先改契约 | 上线后 404/400 |
| 从代码/OpenAPI 生成 | 开发者顺带 | ≈0 | CI diff |
| 从流量学习 + 人工确认 | 安全部门 | 0 | 报告里看 |

产品应同时支持后两条，**不支持“只能手写”**——那是单客户 PoC 形态，不是产品形态。

### 8.3 观察不等于放纵

影子/观察模式必须：逐网关显式开启、启动打 `WARN`、诊断头里标 `X-Gateway-Shadow`、日志与审计里始终记 `would_block`。
否则它会悄悄变成“永久裸奔”。

## 9. 差距与优先级

### P0（没有就不能进场）

| 项 | 为什么是 P0 | 验收 |
| --- | --- | --- |
| **影子模式** | 零改造入场 + 灰度；没有它，契约错了就是事故 | `gateway_enforce off` 时判定照跑、日志 `would_block`、请求放行；开/关两种模式用同一份契约验证“拦截集合一致、放行不同” |
| **观察模式 / 路由发现** | 出测绘报告，是第一份销售物料 | 从 access log / 镜像流量生成候选契约（方法 + 路径模板 + 参数名），人工确认后可直接用于影子 |
| **契约闭包检查** | 防“新增接口忘了声明” | `gateway-contract check`：与路由清单双向 diff，漏声明直接非零退出 |
| **契约版本与审计日志** | 等保要“谁改了哪条规则” | 每次加载记录 `version + sha256 + source + rid`；变更可追溯 |

### P1（能交付单点项目）

| 项 | 验收 |
| --- | --- |
| 指标输出（Prometheus） | 拒绝数按 `reason` 分组；契约版本、加载失败、`would_block` 计数 |
| 审计日志格式（JSON）+ syslog/Kafka | 每行含 `rid`、`reason`、`field`、`rule`、`gateway`、上游地址 |
| 多 worker 一致性（共享内存或管理面下发） | N 个 worker 只拉一次契约；reload 不再必需 |
| 性能基线 | 给出 P99 / 吞吐 / 开启 body 校验后的衰减，形成标书可引用数据 |
| 契约生成器（OpenAPI → 契约） | 未映射语义必须显式失败，不静默丢弃 |

### P2（规模化与合规）

| 项 | 说明 |
| --- | --- |
| 国密 TLS | 自研成本高，优先与国密网关/铜锁（Tongsuo）合作做 TLS 卸载 |
| 管理面 | 多系统、审批、灰度、回滚、报表；这是商业版的主体 |
| 信创适配 | 麒麟/UOS + 鲲鹏/飞腾/龙芯 的构建与验证清单 |
| 等保/密评材料 | 测评对接材料、部署基线、日志留存方案 |

## 10. 商业模式

- **开源核心**：`gateway-core` + nginx 模块（Apache-2.0），换取信任与集成商生态；
- **商业版**：管理面、审计报表、观察/发现平台、国密、HA、多租户；
- **授权方式**：按“被保护 API 数”或“节点数”，离线 license 文件（政企不能联网激活）；
- **渠道**：政企直销难，走集成商/等保测评机构/安全厂商合作。

开源边界的判断标准：**“能不能被一个工程师在一个下午跑起来”** 的部分开源；
需要组织、流程、报表的部分收费。

## 11. PoC 方法（先验证市场，再补产品）

不要先写管理面。用最小成本验证“报告有没有人买”：

1. 选 1–2 个有存量系统的甲方（内部系统也可以）；
2. 以**旁路/镜像或 access log** 接入，只观察不拦，跑 2–4 周；
3. 产出《API 资产与暴露面报告》，至少包含：
   - 实际接口数 vs 文档/契约声明数；
   - 未登记接口清单（方法 + 路径 + 首末次访问时间 + 来源 IP 分布）；
   - 接受未声明字段的写接口清单；
   - 参数画像（长度/类型分布，用于判断合理上限）；
   - 疑似攻击流量统计（这些请求当前是否到了后端）。
4. 用报告谈第二单；有反馈再切影子，再谈强制。

**成功判据**：报告里出现 ≥1 个甲方不知道的接口，且安全负责人愿意拿着它去汇报。
如果报告没人看，说明痛点不成立，趁早止损。

## 12. 风险与明确不做

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **契约维护成本转嫁给甲方** | 100 个系统各写一份契约，项目必然烂尾 | 观察模式 + 生成器；绝不把“手写契约”当交付物 |
| **契约漂移造成生产事故** | 漏声明一条路由 = 线上 404 | 影子模式 + 闭包检查 + 灰度 |
| **被当成 WAF 比价** | 甲方拿特征库数量、虚拟补丁速度比 | 明确“白名单”定位，不比特征 |
| **国密缺失丢标** | 密评是硬门槛 | 合作 TLS 卸载，或排期自研 |
| **开源被白嫖** | 核心被集成商直接交付 | 开源边界设在“单机可用”，规模化能力收费 |
| **和现有网关厂商冲突** | 甲方已有网关，不愿意加模块 | 定位为“能力增强”，可被集成进对方网关 |

明确不做：通用 WAF 规则、限流、鉴权中心、API 文档站、业务规则引擎、流量编排。

## 13. 度量指标

| 指标 | 目标 | 用途 |
| --- | --- | --- |
| 观察期发现的未登记接口数 | ≥1 / 系统 | PoC 成功判据 |
| 影子期 `would_block` 中“误判”比例 | <0.1% | 能否切强制的门槛 |
| 契约覆盖率（已声明路由 / 实际路由） | 100% | 闭包检查的输出 |
| 写接口 `unknown: reject` 覆盖率 | 100% | lint 的输出 |
| 契约从变更到生效的时间 | <5 分钟 | 运维体验 |
| 开启 body 校验后的 P99 衰减 | <10% | 标书数据 |

## 14. 术语

| 术语 | 含义 |
| --- | --- |
| 契约 | 后端（或运维）声明的 API 白名单，JSON，protocol=1 |
| 观察模式 | 只学路由、不判定、不拦截 |
| 影子模式 | 判定但不拦截，只记 `would_block` |
| 强制模式 | 判定并拦截（当前唯一模式） |
| 闭包检查 | 契约与真实路由清单的双向 diff |
| 边界校验 | 路由/方法/字段集合/大小等 HTTP 层规则 |
| 业务校验 | 库存/状态机/权限等，明确不放在网关 |
